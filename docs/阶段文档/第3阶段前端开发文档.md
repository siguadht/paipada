# 第 3 阶段前端开发文档｜3-1 检查点

> 保存时间：2026-09-30。状态：开发中，产品经理认为当前改版视觉“看着还可以”；这不是子阶段完成验收。本文记录此刻可运行的实现，供继续开发与复核。

## 1. 产品行为与边界

用户用邀请码登录，上传房间照片并描述需求。系统先生成一张正面效果图。用户直接在图中点位置，对软装执行删除、替换、改色，或调整整体风格；每次成功编辑得到新图片版本，可恢复旧版。用户确认当前正面图后，系统才以这一版图片为输入生成 2.5D 图。

阶段 2 的旧 `Task` API、最小验收界面和审图流程保留；阶段 3-1 的新流程使用独立 `Design` API 和页面。新流程尚未接入独立管理员审图角色。

当前点选是归一化坐标定位和点击区域的 Q 弹反馈，**尚不能识别并弹起整件家具轮廓**。2.5D 由确认的图片继续生成，但家具数量、位置与等距精度仍需人工验收，不能宣称像素级或结构级一致。

| 后端入口 | `backend/app/main.py` | 注册路由、建表、重启时恢复未完成的 Design 工作 |
| 方案接口 | `backend/app/api/designs.py` | 用户归属、状态校验、编辑上限和任务提交 |
| 工作流 | `backend/app/services/design_service.py` | 初始生成、编辑、版本落库、确认后生成 2.5D |
| 图像服务 | `backend/app/services/image_service.py` | 上传短时源图、调用 Seedream、保存结果图 |
| 数据模型 | `backend/app/models/design.py` | `designs`、`design_versions`、`design_hotspots` |

```text
Next.js 页面 → /api/v1/designs → SQLite 持久化任务状态
                               ↓
                       LLM / Seedream + 临时 TOS URL
                               ↓
                    本地受保护图片 + DesignVersion
                               ↓
                         前端轮询并更新画面
```

前端在生成和编辑时每 2.5 秒查询方案。等待页展示后端实际状态、原照片与可切换的操作引导；计时仅表示本次页面已等待时间，不是模型进度估算。结果页沿已确认的 v5 大图构图，点击图片时才展开编辑面板。2026-09-30 继续复核时修正了 4:3 图片左右留白导致的点击坐标偏移：图片元素与实际可见像素等比，选中标记与点击位置重合。

## 3. 接口契约

所有下列接口要求登录；`{id}` 必须属于当前用户，其他用户访问返回 404。生成和编辑图片也通过受保护文件接口读取。

| 方法 | 路径 | 成功语义 |
| --- | --- | --- |
| GET | `/api/v1/designs/products` | 读取内置商品示意资料；前端按分类展示参考卡片 |
| POST | `/api/v1/designs` | 201，创建正面效果图任务 |
| GET | `/api/v1/designs` | 当前用户历史，最多 50 条 |
| GET | `/api/v1/designs/{id}` | 当前状态、图片 URL、版本和错误 |
| POST | `/api/v1/designs/{id}/hotspots` | 201，给当前 2.5D 图片添加人工标注热点；返回新热点 ID |
| DELETE | `/api/v1/designs/{id}/hotspots/{hotspot_id}` | 删除当前 2.5D 图片上的指定热点 |
| POST | `/api/v1/designs/{id}/edits` | 202，提交点位编辑或风格修改 |
| POST | `/api/v1/designs/{id}/regenerate` | 202，带文字反馈从原照片重新生成整张正面图；旧版保留 |
| POST | `/api/v1/designs/{id}/versions/{n}/restore` | 切换至其他正面图版本并清空旧 2.5D；选择当前版则保持原状态 |
| POST | `/api/v1/designs/{id}/confirm` | 202，锁定当前正面图作为 2.5D 输入 |

创建请求：`{"photo_id":"上传返回的标识","user_input":"改造描述"}`。照片必须由当前用户上传且文件存在。

编辑请求：`{"operation":"delete|replace|recolor|style","x":0.42,"y":0.67,"detail":"墨绿色"}`。`x/y` 是 0–1 的图片归一化坐标；`style` 不需坐标，`delete` 不需 `detail`。坐标会转成模型 `<point>0..999 0..999</point>` 提示。错误统一采用 `{"error":{"code":"...","message":"..."}}`，不返回内部堆栈。

整图反馈请求：`{"feedback":"沙发比例太大，保留原来的窗户和布局"}`，最多 200 字，去空格后不能为空。后端校验用户归属、任务状态和每方案最多 8 次成功修改的共同上限；先持久化 `pending_job`，再用原照片、原始需求和反馈生成新版。成功后新增 `regenerate` 版本并失效旧 2.5D/热点；失败时旧图和版本保持可用。前端在效果图下方展开反馈框，明确提示新一次生图调用。

热点请求：`{"product_id":"p001","x":0.42,"y":0.67}`。仅当前 2.5D 已生成、商品 ID 在内置库中时接受；一张图最多 8 个。`GET /designs/{id}` 的 `hotspots` 数组只返回当前 2.5D 文件与当前正面图版本同时匹配的记录。热点创建响应另含 `added_hotspot_id`，便于前端准确选中新卡片。

主要错误场景：无效邀请码或未登录为 401；他人的方案和图片为 404；缺少点位等业务校验为 400；请求字段校验为 422；任务忙碌或超出编辑次数为 409。初始生成失败进入失败状态；编辑与 2.5D 失败保留原图并给可读错误。前端不得把 MOCK 图当真实效果。

## 4. 状态、版本与恢复

```text
pending → understanding → rendering_front → front_ready
front_ready/completed → editing → front_ready
front_ready → rendering_iso → completed
```

初始生成失败进入 `failed`。编辑或 2.5D 失败回到 `front_ready`，保留上一个可用正面图。每次成功编辑新增一条 `DesignVersion`，主记录保存当前版本编号、图片路径、编辑历史和状态；切换到其他版本清除已生成的 2.5D，避免不同版本错配。重复选择当前版本不修改状态，也不会误删已生成的 2.5D；前端将当前版按钮置为不可点击。2.5D 页显示来源正面图版本和该版最后一次编辑记录，初始设计说明若已过时则不冒充当前逐件商品说明。

产品经理选择由用户在 2.5D 图片上点位置并选参考商品。热点记录单独持久化于 `design_hotspots`，包含方案 ID、2.5D 图片文件名、来源正面图版本、商品 ID 和归一化坐标。编辑正面图成功或切换正面图版本后清掉旧图热点；即使出现异常遗留记录，读取时也会按图片文件名和版本过滤。热点创建与删除均复核方案归属，用户只能改自己的方案。此流程不调用额外模型；卡片只说明人工标注的参考商品，不宣称自动识别。

提交编辑和 2.5D 前先写入 `pending_job`，进程重启时由 `backend/app/main.py` 扫描未完成状态并尝试重跑。数据保存在项目 `data/` 下的 SQLite 与图片目录；该目录被 Git 忽略。此机制已做自动化重启恢复验证，尚未作为正式线上任务队列验收。

## 5. 模型、费用与安全

- 房间理解由当前火山方舟 LLM 完成；图片初生、点位编辑和 2.5D 使用已配置的 Seedream 5.0 Pro。2.5D 的输入是用户确认的当前正面图。
- 图像源文件由服务端上传至 TOS，模型读取短时授权 URL。结果图片下载到本地受保护目录；临时源对象调用后尝试删除。接口不向前端传模型密钥或 TOS 凭据。
- 无模型 Key 时使用带明显 `MOCK` 标识的离线图片，只验证状态与交互。
- 每个方案最多 8 次成功编辑，由后端确定性校验。图片生成仍会产生模型费用，具体账单以平台为准。
- 上传格式、大小与真实文件类型由原有上传接口校验；所有方案、上传图和生成图按登录用户归属读取。
- 商品库目前为 28 件示意资料，前端提供分类卡片浏览、替换参考选择，以及由用户手动对应到当前 2.5D 图片的热点。没有单品图片、真实库存或购买链接；卡片用“商品图待补”占位，价格未经核实。未标注的商品仍只是独立灵感资料。

## 8. 接续命令

从项目根目录分别启动后端和前端；端口 8002 是本地并行调试约定，若 8000 空闲，可按 README 改回 8000 并对应调整前端 API 地址。

```bash
cd backend
.venv/bin/uvicorn app.main:app --host 127.0.0.1 --port 8002
```

```bash
cd frontend
NEXT_PUBLIC_API_BASE_URL=http://127.0.0.1:8002/api/v1 npm run dev
```

前端打开 `http://127.0.0.1:3000/`。环境配置位置见项目 README；任何密钥、邀请码本身和用户图片都不写入本文件。
